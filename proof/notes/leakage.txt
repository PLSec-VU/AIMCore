Leakage proof: what it says, how to run it, and how to chase a failure.
=======================================================================

WHAT IS PROVED
--------------
The attacker sees every request the core puts on its memory interface, cycle
by cycle: the address of each instruction fetch and the kind, address and width
of each data access, but no data (Proof.Leakage.Model.Obs). These are the
accesses a cache in front of the core receives, with their timing.

The leakage is the constant-time one (Proof.Leakage.Model.L): per instruction,
its class and source registers (functions of the code), its control flow
(branch taken or not, jump target) and its data address. Proof.Leakage.Induction
holds leakBase and leakStep0..3, each in its own module
(Proof.Leakage.Induction.Base, Step0..3). leakBase is the first hop out of
reset, which the steps do not cover because the reset state does not satisfy
the invariant; it also says the simulator starts in the same state for every
program. leakStep0..3 are the hops that start in the invariant, one per hop
length. Together with the functional proof (Proof.Functional.Induction) they
give: two runs whose ISA-level constant-time leakage traces agree make the same
memory requests, cycle by cycle.

There is no assumption beyond the functional invariant, which describes the
core attached to memory that answers every request in the next cycle
(Proof.Machine.stepSys). In particular there is no assumption on addresses or
on self-modifying code: a store that overlaps the instruction in decode stalls
the core, and the stall depends only on the store's address, which the leakage
carries.

BEHIND A CACHE
--------------
Proof.Machine.stepCachedOut is the core in a loop with a server, the cache in
front of memory (Proof.Machine.cacheServe), as stepSysOut is the core in a loop
with ideal memory (Proof.Machine.idealServe). Both answer a read with exactly the
bytes it asks for (Proof.Machine.readResp), so the cache can give the same answer
as memory although it holds only the read's block.

The composition theorem of the paper turns the core's leakage proof behind
ideal memory into one behind the cache, given three more things, all proved in
Proof.Cache.Induction:

  * a server proof for the cache (Proof.Cache.Server), for the four-line cache
    Memory.Cache.Cache4 and a miss penalty of three. Its driver is the hop of a
    request: the request, then no request until the response is ready. Invariant:
    no miss pending, cache coherent with memory (Memory.Cache.coherent4, which
    also bounds tags to the 28 bits an address has: a valid line with a wider
    tag is never invalidated by a write to its block). Flush: the memory.
    Censor: the cache without its data. Simulator: the cache's own hop on the
    censored cache in front of a memory of zeros. srvInitP: the empty cache
    starts in the invariant. srvRefineP: the hop of a request ends with ideal
    memory's response and memory. srvLeakP: the ready bits of the hop and the
    next tags follow from the tags and the observation of the request
    (Proof.Leakage.Model.obsReq, which is also the core's attacker; it takes
    every request carrying a value as a write, as both memories do, though the
    core never fetches with one);
  * patience of the core: stallStep (a stall cycle changes nothing but the
    control lines, which Core.withCtrlReset resets before any stage reads them),
    and waitStep (after a data read the core waits);
  * stallsOnReadsP: the cache answers late only to a data read.

test/CompositionSpec.hs checks the same statements concretely, and the
theorem's conclusion end to end: the cached core's bus trace equals the one
computed from the leakage alone, by the core's simulator followed by the
cache's. Cache4 is DirectMapped 4 written without Vec, which the verifier cannot
execute; the tests check that the two agree.

RUNNING
-------
Use Bitwuzla, not Z3. Z3 does not finish these queries in useful time.

  SBV_Z3=/opt/homebrew/bin/bitwuzla SBV_Z3_OPTIONS="--produce-models" \
    stack test --no-run-tests > /tmp/model.txt 2>&1
  grep "^\[RECV\]" /tmp/model.txt

Build at -O1 or above. Under `stack build --fast` GHC creates no unfoldings,
the plugin cannot see through cross-module calls, and it aborts with
`Unbound variable in symbolise: <name>` -- a BUILD failure, easily misread as a
failed proof.

CHASING A `sat`
---------------
The plugin cannot print counterexamples containing arrays: SBV fails to parse
them back and the build dies with `version (...) /= storageVersion (0)`. The
model is still in the log, as the raw `get-value` responses, in SBV variable
order -- the KState fields, then Core.Input, RegArr, MemArr, then the witness
RegIdx and Address.

Decoding that by hand is a last resort. Two cheaper moves, in order:

  1. Split the PREMISE to find which shape fails: copy the failing step module
     and add a premise on the driver case, e.g. `loadHazardD sys` or its
     negation, separating the shapes that reach the same hop length.

  2. Split the CONCLUSION to find which conjunct fails -- the state equality or
     one of the four observation slots. Assume the full premises and assert one
     piece at a time.

Then reproduce concretely with test/LeakageSpec.hs, whose arbitrary-state
generators range over the same space the symbolic properties quantify over
(unreachable states included) and give a shrunk, printable counterexample. For
the cache's obligations the generators of test/CompositionSpec.hs play that
role (genSrv, genReq: tags no address has, fetches carrying a value). If
the search cannot find it, the generator is missing a shape: check that the
instruction forms involved are actually generated before concluding the state
is unreachable.
